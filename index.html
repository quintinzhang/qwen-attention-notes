为什么面试官总绕回底层

Agent 开发面试，为什么会考 Attention？

先给结论：Agent = 「模型 + 工具调用循环」，而循环的每一轮都在把上下文越拉越长。系统提示词、工具 Schema、历史对话、每轮的工具返回结果……全部堆进同一个上下文窗口。所以 Agent 开发工程师每天真正在对抗的问题，恰好就是 Qwen 这条演进史解决的四个问题：

📖 先对齐几个词（全文统一，后文不再重复解释）

token：模型处理文字的最小单位，约等于一个字或半个词——模型眼里没有汉字，只有一串 token。上下文窗口：一次能装下的 token 数量上限，相当于模型的「工作内存」，装不下的内容它完全看不见。RAG（检索增强生成）：先从外部知识库里搜出相关材料，再塞进上下文让模型作答——相当于「开卷考试」。系统提示词 / 工具定义：写给模型的长期指令、以及可用工具的清单（名称加参数说明）。TTFT：Time To First Token，首字响应时间——从你发出请求到第一个字蹦出来的延迟。后文的 Prefill / Decode、FLOPs、logits 等词，同样会在首次出现处当场解释。

面试官问「1M 上下文能不能取代 RAG」「为什么你的 Agent 越跑越慢」，考的不是背参数，而是你能不能从 Attention 的工作原理出发，解释这些工程现象并给出分层方案。这份文档就按这个目标来组织：每章先讲第一性原理，再给后端类比，最后落到 Agent 场景怎么答。

🔗 本章 Agent 连接点

一个典型 Agent 请求的上下文构成：系统提示词 + 工具定义（几乎不变） + 多轮对话与工具轨迹（每轮都在增长）。「不变的头部」和「增长的尾部」会贯穿全文——第 04 章的前缀缓存、第 07 章的上下文管理，都建立在这个结构上。

01
第一性原理 · 从加权平均推起

Attention 从零推导：它到底在算什么

1.0 预备知识：三个数学工具（Java 视角，10 分钟）

全文只用到三个数学工具，全部可以当成 Java 代码看。已经熟的同学直接跳到 1.1。

工具一：向量 = 一串有序的数字。模型不认识汉字，只会算术，所以第一步是把每个词翻译成一串数——这就是「向量」，你当成 double[] 看就行：

// 一个词 = 一个向量（真实模型几千维，这里 3 维示意） double[] 猫 = { 0.9, 0.2, -0.1 }; double[] 狗 = { 0.8, 0.3, 0.0 }; // 和"猫"很接近 double[] 贷款 = {-0.7, -0.4, 0.6 }; // 和"猫"差得很远

每一位叫一个「维度」，可理解为某个语义特征上的取值——类比用 [价格, 重量, 评分] 描述一件商品；只是模型的几千个维度没有人类可读的名字，是训练自动学出来的。真正重要的是：含义相近的词，向量方向就相近，于是「语义」变成了可计算的几何关系。这张「词 → 向量」对照表叫 embedding 表，本质是巨大的 Map<String, double[]>，表里的数字全部来自训练。

工具二：点积 = 相关度打分器。两个向量对应位置相乘、再全部加起来：

dot(a, b) = a₁×b₁ + a₂×b₂ + a₃×b₃ + ... dot({1,2}, {2,4}) = 1×2 + 2×4 = 10 → 同方向（语义近）→ 大正数 dot({1,0}, {0,5}) = 1×0 + 0×5 = 0 → 互相垂直（无关）→ 约 0 dot({1,2}, {-2,-4}) = -2 - 8 = -10 → 反方向（相反）→ 负数

直觉：两串数字在相同维度上互相印证，分数就高。Attention 的打分 q·k 用的就是它。

工具三：Softmax = 把任意分数变成百分比预算。输入 N 个任意实数（可以负），输出 N 个正数、总和恰好 1 的权重——相当于「100% 的注意力怎么分配」。做法就两步：先对每个分数算 e 的幂（正数化 + 拉大差距），再除以总和（凑成 100%）：

softmax(zᵢ) = e^(zᵢ) / Σ e^(zⱼ) 例：分数 { 2.0, 0.5, 5.0, -1.0 } 指数 { 7.4, 1.6, 148, 0.4 } 总和 ≈ 157 权重 { 4.7%, 1%, 94%, 0.3% } ← 和恰好 100%

记两条性质就够用：① e 的幂永远是正数，权重合法；② 分数差被指数放大——差 1 分权重差约 2.7 倍，差 5 分差约 148 倍，所以分数大的拿大头但不垄断（小的仍留残余）。分数差距过大时小权重会趋近 0%，这个伏笔第 05 章回收。

1.1 任务本质：一次「内容感知」的加权平均

大模型每一步只做一件事：根据前面的所有 token，预测下一个 token。关键在于：前面每个词的重要程度不一样。处理「她饿了」的「她」时，「小明」很关键，「今天天气晴」几乎无用。

所以模型需要一种机制：对历史信息做加权汇总，且权重由内容相关性决定。这就是 Attention 的全部本质：

输出 = Σ ( 权重ᵢ × 信息ᵢ ) 其中 权重 = Softmax( 相关性分数 )

Attention 不是黑魔法，是一次内容感知的加权聚合。类比后端：MapReduce shuffle 之后按 key 做加权 merge，只不过「权重」本身也是现场算出来的。

1.2 Q / K / V：同一份数据的三种角色

每个 token 的向量要扮演三个角色，所以经过三张不同的「配方表」（行话叫投影矩阵），把同一份向量重新组合出三份表示：

角色职责后端类比
Query我在找什么样的信息？SQL 里的 WHERE 条件
Key我这里有什么可供匹配？索引里的词条
Value匹配成功后我真正提供的内容索引指向的数据行
q = x·Wq k = x·Wk v = x·Wv
score(i,j) = qᵢ·kⱼ / √d → Softmax → 对 vⱼ 加权求和

这里的「向量 × 矩阵」不用深究数学：把它当成「按一张训练学来的配方表，把向量的各个维度重新调配一遍」就够了，配方表里的数字是训练自动学出来的。三张配方不同，所以同一份底稿能变出三个分工不同的分身。

/√d（除以维度的平方根）是一个防溢出除数：维度越多，点积里相加的项就越多、数值自然越大，除一下把它压回稳定范围。记住这条线——第 05 章「分数失控」就是它没压住的故事。

多头（Multi-Head）：一组 q/k/v 只能捕捉一种关系。把向量切成 32 份各自独立做 Attention，等于 32 个并行的小检索器——有的盯语法、有的盯指代、有的盯邻近位置。类比：同一条日志流，N 个 consumer 各自订阅自己关心的字段。

1.3 因果遮罩：一条不可变事件日志

模型逐词生成时（这类逐词生成的模型行话叫 decoder）只能看过去、不能看未来——否则训练时的「预测」就是作弊。实现上靠一张许可表（行话叫 mask）：每一行只放行它自己和更早的位置。用后端视角看更妙：整段上下文是一条 append-only 的不可变事件日志，已写入的历史永不改变。这个性质马上在第 04 章给 KV cache 铺路——不可变数据天然适合缓存，不用考虑失效。

🎙 面试 30 秒 · 技术口径

Attention 本质是「由内容相关性决定权重的加权平均」。每个 token 经三个投影变换出 Query/Key/Value：Q 与所有 K 打分，Softmax 归一化后对 V 加权汇总；多头是把向量切分后并行捕捉多种关系；因果遮罩保证只看过去，等价于 append-only 日志。

🔗 Agent 连接点

Agent 框架里的「工具选择」，思想上就是一次 Attention 式检索：当前任务意图（Q）与每个工具的名称/描述/参数说明（K）匹配，选中后再取工具的完整 Schema 并执行（V）。理解了这一点，你就明白为什么工具描述写得好不好，直接决定模型选不选得对工具——描述就是 Key，Key 的质量决定检索命中率。

02
第一个被逼出来的机制

位置编码：模型不知道谁在前谁在后

2.1 没有位置信息时，模型看到的是「一袋词」

先回应一个自然会产生疑问：「既然后面会算『相隔多远』，那不就能分清语序了？」——顺序反了。在没有位置编码时，打分公式 score = q·k 里压根没有「位置」这个输入，连「相隔多远」这个概念都不存在。打分只看两个词的内容：score(吃,我) 在两句话里是同一个数，score(吃,饭) 也是。于是整句话的效果是一袋无序的词：

// 没有位置编码的 Attention，效果上等价于把句子装进词袋： Map 我吃饭 = {"我":1, "吃":1, "饭":1}; Map 饭吃我 = {"饭":1, "吃":1, "我":1}; 我吃饭.equals(饭吃我) // → true，模型眼里是同一句话

数学上这叫置换等变：输入换序，输出只是跟着换位，任何「汇总整句」的计算都区分不出它们——「我」和「饭」谁是主语，信息在打分那一刻就丢了。

所以结论是：位置信息必须额外注入——不是设计选择，是必须补的课。补的思路：给每个 token 发一个「座位号」。

2.2 第一代方案：加绝对位置，以及它的失败

最直白的做法：给每个位置配一个向量，直接加到输入上：

xᵢ = TokenEmbedding(tokenᵢ) + PositionEmbedding(i)

位置向量可以查表训练（可学习式），也可以用固定正余弦公式生成（正弦式）。两种都有硬伤。先约定一个后文反复出现的词：分布外 = 训练时从没见过、超出经验范围的输入，模型遇到它容易乱来：

但两者还有一个更根本的共同问题：注入的是「你在第几行」，而语言真正关心的是「你们相隔多远」。

2.3 关键一课：相对距离是「有符号」的——语序就藏在正负号里

现在回答那个最容易卡住的问题：「我吃饭」和「饭吃我」里，任意两词的间隔长度都相同（吃和饭都相邻），相对距离凭什么能区分它们？

因为距离不是「隔多远」这么简单，它带方向、有正负。站在「吃」的视角看：「饭在我后面一格」记作 +1，「饭在我前面一格」记作 −1——这是两个不同的数。而「在吃的前面还是后面」，恰恰就是主语和宾语的区别：

站在「吃」的视角我 吃 饭饭 吃 我
「我」在哪个槽位−1（前面 → 主语槽）+1（后面 → 宾语槽）
「饭」在哪个槽位+1（后面 → 宾语槽）−1（前面 → 主语槽）

于是模型可以学到一条方向性语法：「−1 槽里的词是施动者（主语），+1 槽里的词是受动者（宾语）」。两句话里坐进 ±1 槽的词正好互换，语义判断随之相反。相对距离能区分语序，靠的不是「隔多远」，而是「在前还是在后」这个正负号。

顺带解开一个可能的纠结：2.2 说 (10,12) 和 (10010,10012) 等价，那把两个词交换位置也等价吗？不等价。平移 ≠ 交换：整体平移（所有位置一起 +10000）不改变任何一对词的相对距离；而交换两个词会让它们之间的距离正负反转（+1 变 −1）——在模型眼里是完全不同的信号。

2.4 RoPE：把「有符号的相对距离」旋进点积

RoPE（Rotary Position Embedding，旋转位置编码）换了思路：不往输入上加位置，而是在每层 Attention 里按位置旋转 Q 和 K。把 q、k 的每小段维度想成平面上的指针：位置 m 的 token，指针旋转 m×θ。关键在于角差有正负——后面的词转得多、前面的词转得少，两根指针的夹角因此带上方向：「+1 格」和「−1 格」会给出不同的打分，2.3 说的方向信息就这样进入了注意力。

重要转折：RoPE 解决的是「怎样表示相对位置」，没有解决「模型会不会用没见过的距离」。训练时最大相对距离 4K，推理时来了 100 万——m−n = 999998 这个角度差模型从未见过。于是进入第二个问题。

🎙 面试 30 秒 · 技术口径

纯 Attention 打分只看内容、不含位置，效果等价于词袋——「我吃饭」和「饭吃我」无法区分，所以位置必须额外注入。早期方案是加绝对位置向量：可学习式超表即越界，正弦式能算但属分布外。RoPE 改为按位置旋转 Q/K，点积只依赖相对距离 m−n——注意这个距离有正负：「你在我前面一格」（−1）和「后面一格」（+1）是不同的旋转角差、不同的分数，模型由此学到方向性语法（−1 槽主语、+1 槽宾语），同时整体平移不影响打分（平移不变）。不同维度不同频率，高频辨近处、低频承远景。

🧑‍🏫 把这章讲给别人（三句话脚本）

① 没有位置编码时，Attention 等于词袋，「我吃饭」和「饭吃我」是同一句话——因为打分公式里根本没有位置；② 所以给每个词发座位号，但绝对座位号外推差，RoPE 改成「按座位旋转 QK」，打分只看相对关系；③ 最容易被追问的点：相对距离有正负——前面一格是 −1、后面一格是 +1，主语宾语的区别就藏在这个符号里（可再补一句「平移 ≠ 交换」）。

🔗 Agent 连接点

Agent 的对话常常「第 50 轮引用第 2 轮的约定」——跨长距离的指代与状态回溯，正依赖相对位置的编码质量。另外 Prompt/Prefix Caching 能成立，位置编码是隐含前提：固定前缀（系统提示词+工具定义）的 K/V 按各自位置算好缓存后，只要前缀不变，后续请求直接复用、语义完全一致。这就是为什么「把稳定内容放在上下文最前面」是 Agent 提示词工程的第一条军规（第 04、07 章展开）。

03
第二个问题 · 长度外推

能算出来 ≠ 模型会用：YaRN 与 DCA

3.1 熟悉的影子：分布漂移

只练过百以内加减法的学生拿到百万位的题：题目写得出来，但他不会算。换成后端语言：生产流量画像和压测时完全不同，容量模型直接失效。训练时所有 head 只见过 0~4K 的相对距离谱，超过之后轻则注意力散焦，重则近处分辨率被破坏、长文准确率骤降。本章标题里的「长度外推」指的就是这件事：让模型在训练时没见过的更长文本上，仍然正常工作。

所以要把两个问题分开——面试最爱在这里挖坑：

问题谁解决注意
能不能表示远的位置？RoPE（已解决）—
模型能不能在远处正常工作？YaRN / DCA目的是长度外推，不是降低计算复杂度

3.2 YaRN：不同频率区别对待的缩放

朴素做法：把 16K 位置整体压缩进训练过的 4K 区间（线性插值）——把大幅地图缩印塞进旧相框，整体进去了，相邻街道挤成一团。RoPE 各维度频率不同：高频辨近处、低频承远景，一把尺子统一压缩必然顾此失彼。YaRN 的思路是分级处理：

3.3 DCA：分块重组相对位置

DCA（Dual Chunked Attention）是另一条路线，Qwen2.5-1M 用它把推理窗口从训练的 256K 外推到 1M。核心思想：别让巨大的 i−j 直接进入旋转角度——把长序列切块后重组位置体系，块内保持小距离（模型熟悉），跨块距离用另一维坐标表达，使所有有效距离都落在训练见过的范围内。

🎙 面试 30 秒 · 技术口径

长度外推要和复杂度优化分开。两条主流路线：YaRN 式缩放——利用 RoPE 高频辨近、低频承远的性质分频处理并修正温度；Qwen2.5-1M 路线——先训练到 256K，推理时用 DCA 把位置体系分块重组，避免训练范围外的巨大相对距离进入 softmax。前者改造「尺度」，后者改造「坐标系」，目的都是让模型在没训过的长度上正常工作。

🔗 Agent 连接点

这是 Agent 面试最高频的知识迁移点：「模型支持 1M 上下文」≠「1M 上下文都好用」。外推技术解决「模型会读」，但长上下文还有两大独立难题：中间信息容易被忽略（lost in the middle），以及成本随长度上涨（第 04 章）。所以「1M 上下文取代 RAG」是个伪命题——第 07 章给出完整答法。

04
第三个问题 · 推理成本

KV cache：一条不可变日志的缓存账单

4.1 逐 token 生成的重复计算与缓存机会

模型生成是一步一步来的，如果每步都从头算，生成 1000 个 token 就是 1000 次近似全量重跑。好消息是历史不会变——因果遮罩保证了历史 token 的表示永不受未来影响（第 01 章的不可变日志）。所以每层里历史 token 的 K、V 可以算一次、永久复用，这就是 KV cache。

4.2 GQA：给 cache 减副本

cache 体积正比于 KV 头数，那就砍头数——只砍 K/V，不动 Q：

4.3 真正省计算量（FLOPs）：稀疏 Attention

实测规律：长文本里 attention 高度稀疏——大部分头只看邻近 token（对角线）、或某一列（如句首）、或少数块状区域。只算可能重要的块即可（MInference 是代表工作）。

⚠ 容易踩的坑 · 面试高分点

「看似稀疏」≠「真稀疏」：如果先把完整矩阵算完、再用 mask 盖掉一部分，计算量一次都没省（FLOPs = 浮点运算次数，衡量「一共做了多少次算术」的单位）——就像 SQL 写了 WHERE 但没走索引，照样全表扫。真正的稀疏必须在 kernel 执行前决定跳过哪些块（kernel：GPU 上跑的底层计算程序，先理解成「真正干活的那段代码」）。配套手段 chunked prefill（超长 prompt 分批送入）则负责压平中间激活的显存峰值。

再补一个阶段划分：模型收到请求后有两个阶段——Prefill（先把整个 prompt——即你发给模型的全部输入文本——并行处理一遍，像批处理任务，吃算力）和 Decode（之后逐 token 生成答案，像 N+1 场景，吃带宽）。两者瓶颈不同，所以 Qwen2.5-1M 的组合拳是「稀疏 Attention（救 Prefill）+ GQA（救 Decode）」，不可互相替代。

🎙 面试 30 秒 · 技术口径

生成是逐 token 循环；因果性保证历史 K/V 不变所以可缓存。KV cache 让每步免于全量重算，但显存随长度线性增长（56KB/token 量级，1M≈56GB），且 Decode 每步要完整读取一遍，瓶颈在显存带宽。三板斧各管一层：GQA 减 KV 份数（省搬运不省 FLOPs）；稀疏 Attention 在 kernel 前跳块（真省 FLOPs，救 Prefill）；chunked prefill 平滑显存峰值。

🔗 Agent 连接点

这一章是 Agent 成本优化的理论根基，直接对应三件你天天在做的事：① Agent 多轮对话每轮都把更长的历史重新 prefill → 响应越来越慢，除非命中前缀缓存；② 系统提示词+工具定义几乎不变——把它们放最前且保持字节级稳定，前缀 KV 就能跨请求复用，TTFT 大幅下降；③ 工具返回的大段 JSON 塞进上下文 = 每一轮都在为它付 KV 读取的钱——工具结果该截断就截断。

05
第四个问题 · 训练稳定性

模型越大，打分越容易失控

📖 先补两个词：训练 / 梯度（本章的主角）

训练：拿海量文本反复让模型做「预测下一个 token」的填空题，每次答错就微调它内部的数字（参数）。梯度：批改后发给每个参数的整改单——「你往这边调多少，错误会变小」。训练崩溃最常见的形态，就是整改单本身出了问题（数值爆炸或归零），整个模型随之失灵。

这个问题在推理侧看不见，却能把几百张显卡的训练任务整个带崩。Attention 的打分是点积：模型变大后，某些头的 Q/K 数值越滚越大，点积可以非常大，经 Softmax 后分布退化成近乎 one-hot（one-hot = 只剩一个 1、其余全是 0，也就是「全押一个选项」）——类比负载均衡彻底失效，全部流量倾斜到一台服务器；后果是整改信号失真、错误上下乱跳，甚至算出 NaN（Not a Number，数值溢出后的错误值）。/√d 只防住了「项数多导致的自然变大」，防不住训练过程本身把数值越推越大。

🎙 面试 30 秒 · 技术口径

规模变大后 Q·K 点积膨胀使 softmax 退成单点独热（全押一个选项），整改信号失真，训练震荡发散。解法逐代加强：√d 除数和 QKV-bias → Qwen3 的 QK-Norm 直接归一化 Q、K → Qwen3-Next 的零中心 RMSNorm（把数值拉回 0 附近）加 weight decay（约束参数「别长太大」），并用输出门控消除 attention sink（注意力长期倾泻在句首某 token 上的病态模式）。核心思想一致：限制打分尺度的自由度，换取大规模训练稳定。

🔗 Agent 连接点

面试里这章的用法是「选型判断」：知道某代模型用了 QK-Norm / 零中心 norm，意味着它在大规模、长序列训练上更稳——而 Agent 的长程多轮任务正是模型训练分布里最苛刻的部分。被问「为什么新模型跑长任务更稳」，你能从打分尺度失控一路讲到训练稳定性，这已经超过大多数候选人。

06
换一种记忆方式

线性注意力与混合架构：从明细表到物化视图

6.1 标准 Attention 的两个原罪

数一数固有开销：① 状态大小随长度 N 正比增长——KV cache 随上下文线性增长（第 04 章的账单）；② 计算量随 N 平方增长（长度翻 10 倍、计算量翻 100 倍）——Prefill 要两两打分（百万 token 单头单层约 5×10¹¹ 对）。有没有办法让记忆总量恒定？有——放弃保存全部明细，改存聚合摘要（数据库行话：用「物化视图」——提前算好、存起来的汇总表——代替明细表）。

6.2 线性注意力：UPSERT + 遗忘的固定状态

维护一个固定大小的状态矩阵 S，每读入一个 token 就对 S 做一次大小固定、不随历史增长的更新；查询时直接与 S 交互，不再遍历历史。两个关键机制：

  • Delta rule（UPSERT 语义；UPSERT = 有则更新、无则插入）：新事实与已有记忆冲突时，修正而非叠加。先读「小明拿着钥匙」再读「钥匙交给小红」→ 持有者字段从小明更新为小红，而不是两个人并存。无脑累加只会堆积矛盾记忆。
  • Gate（遗忘门）：类似 TTL（过期时间）/衰减因子，控制哪些旧信息保留、哪些被冲淡。

6.3 Qwen3-Next 的答案：3:1 分层混搭

🎙 面试 30 秒 · 技术口径

标准 attention 有两个固有开销：状态随 N 线性增长的 KV cache 和 N² 打分。线性注意力把历史压缩进固定状态（delta rule 做 UPSERT、gate 做衰减），代价是无法无损保存明细、精确召回变弱。Qwen3-Next 按 3:1 混合：多数层用 Gated DeltaNet 维护高效摘要，少数层保留全注意力负责精确检索，外加输出门控与部分维度 RoPE。一句话：效率和精度按层分工，不整模二选一。

🔗 Agent 连接点

Agent 是「精确召回」需求最重的负载：复制上一次工具调用的参数、引用第 3 轮的 API 约定、对历史代码做精确 diff——这些任务撞上「只有压缩记忆」的模型就会出错。面试被问「Agent 对模型架构有什么要求」，你可以答：需要无损的精确召回通道，这正是混合架构保留 25% 全注意力层的原因；同时线性层把长 run 的上下文成本打下来，两件事在架构层面就被安排好了。

07
实战 · 答题骨架

Agent 面试七问：把原理换成答案

下面七道题是 Agent 开发面试中出现频率最高、又最能用前六章原理解答的问题。每题给「面试官在考什么」和「答题骨架」——骨架建议背下来，展开时往原理上靠。

Q1

你的 Agent 跑着跑着上下文爆了 / 效果下降，怎么办？

面试官在考：Context Engineering 的分层策略，以及你是否知道每层的代价

  • 先量化：审计 token 构成——系统提示词 / 工具 Schema / 历史 / 工具返回各占多少，再对症下药；
  • 截断：滑动窗口只保留近 N 轮，最便宜，但丢早期约定（长程任务慎用）；
  • 压缩：把旧轮次摘要成 memory note 再丢弃原文——本质是用「聚合视图」换「明细」（第 06 章原理的应用层翻版），丢细节风险同源；
  • 外置：工具结果、大文件落库，需要时检索回来——把「精确召回」交给 RAG 而不是上下文；
  • 换长上下文模型：可行但记住第 03/04 章——外推≠好用，且每轮成本随长度涨。

加分点：指出这套权衡和模型架构层的权衡同构——全注意力（存明细）vs 线性注意力（存摘要）vs 检索（外置存储），Agent 应用层只是把同样的选择题再做一遍。

Q2

模型都有 1M 上下文了，还需要 RAG 吗？

面试官在考：是否理解「外推成功」与「长上下文好用」是两回事

  • 会读 ≠ 读得好：DCA/YaRN 解决「训练窗口外正常工作」，但 lost in the middle、多跳组合检索的精度仍随长度衰减；
  • 读得起吗：KV 显存与 prefill 延迟随长度增长（第 04 章账单：1M≈56GB/请求），RAG 只送相关片段，天然便宜；
  • 管得了吗：知识库需要更新、鉴权、审计——塞进上下文就失去了数据治理；
  • 结论：互补而非替代。一次性深度阅读（整库代码理解、长文档审阅）用长上下文；大规模、需检索、需治理的知识用 RAG；生产系统通常是「RAG 粗筛 + 长上下文精读」的混合。

加分点：主动提大海捞针（NIAH）测试的局限——单针能捞对，不代表多跳、抗干扰的真实负载能做好（详见 Q7）。

Q3

Agent 多轮之后响应越来越慢、越来越贵，为什么？怎么优化？

面试官在考：Prefill/Decode 成本模型是否装在心里

  • 慢的根源：每轮都要对「全量历史」做 prefill（两两打分，随长度超线性涨）；Decode 每生成一个 token 要完整读一遍 KV cache（带宽瓶颈，N+1 类比）；
  • 优化一 · 前缀缓存：稳定前缀跨轮复用 KV（图 14），TTFT 大幅下降；
  • 优化二 · 控制尾部：工具结果截断、历史压缩/裁剪（Q1 策略）；
  • 优化三 · 选对架构：混合线性注意力的模型（Qwen3-Next 系）长上下文单价更低；MoE（专家混合：内部有很多「专家」子网络，每个 token 只调用其中少数几个）让激活参数（真正参与计算的参数量）小、吞吐高；投机解码/MTP（先一口气猜几个 token、再批量校验，错了才回滚）提升生成速度。

加分点：把「慢」拆成 TTFT（首字延迟，prefill 决定）和 TPOT（每个字的生成时间，即吐字速度，decode 决定）分别归因，再分别给方案——这是后端工程师做延迟归因的直觉迁移，面试官会眼前一亮。

Q4

为什么系统提示词和工具定义要放在最前面、且保持字节级稳定？

面试官在考：Prefix Caching 的原理级理解

  • KV cache 按位置复用：前缀完全一致 → 这部分 K/V 直接复用，只有尾部增量计算；
  • 前缀哪怕改一个标点，从改动处往后的 KV 全部失效——所以易变内容（时间戳、随机 ID）绝不能插在最前面；
  • 推论：稳定内容前置、动态内容靠后；多 Agent 共享同一系统提示词时收益最大。

加分点：能连回第 02 章——位置编码的确定性（同位置同旋转）是「同前缀同 KV」成立的前提。

Q5

模型的「记忆」分几种？Agent 分别怎么用？

面试官在考：记忆分层与各自的工程边界

  • 参数记忆：训练时写进权重，容量大但不可更新、不可删除；
  • 上下文记忆：Attention 直接可达，精确但贵（第 04 章）且受窗口限制；内部又分两档——全注意力层的「无损明细」与线性层的「压缩摘要」（第 06 章）；
  • 外置记忆：RAG / DB / 文件系统，可更新、可鉴权、可审计，但依赖检索质量。

加分点：指出 Agent 的 memory 系统（摘要、向量库、知识图谱）本质是在应用层重演模型架构层的记忆权衡——「什么放明细、什么做摘要、什么外置」。

Q6

给 Agent 选底座模型，你会看什么指标？

面试官在考：是否把模型特性翻译成 Agent 场景的工程指标

  • 真实可用上下文：以 NIAH/多跳实测为准，不看标称（Q7）；
  • 成本结构：MoE 总参/激活参数比（如 80B 总参、A3B 激活：每个 token 只用约 3B 参数 → 吞吐高、单价低）、缓存命中计价；
  • 长 run 稳定性：训练稳定性技术（QK-Norm 等）是间接信号；超长任务看是否出现行为劣化；
  • 吞吐技术：是否支持投机解码/MTP（影响 TPOT）；
  • Agent 基本功：工具调用格式遵循、多工具并行、指令漂移抵抗。

加分点：说出「混合线性架构的模型长上下文单价低，但要验证精确召回场景（参数复制、代码 diff）」——一句话同时展示架构理解和场景意识。

Q7

什么是大海捞针测试？为什么 Agent 真实负载比它更难？

面试官在考：对长上下文评测的理解深度

  • NIAH：在超长文本中埋一句事实（如「密码是XX」），测试模型能否在任意深度召回——考察的就是第 03 章「外推后还能正常工作」；
  • 真实负载更难的四点：①多跳——答案要组合分散在两处的信息；②干扰——几十个工具返回全是相似噪声；③位置偏置——lost in the middle，中部信息最容易被忽略；④精确复制——工具参数、代码片段必须逐字正确，对应「精确召回」能力；
  • 结论：NIAH 通过是必要条件而非充分条件；评测 Agent 应构造多跳+干扰的负载。

加分点：把④连回第 06 章——这正是混合架构保留全注意力层的原因，评测和架构在设计上是对偶的。

🎙 90 秒电梯稿 · 先讲原理，再落 Agent（可直接背）

标准多头加 RoPE 是现代模型的基线：Attention 做内容寻址的加权汇总，RoPE 按位置旋转 QK，使打分只依赖相对距离。之后的演进围绕四个独立问题。第一是推理成本：因果性保证历史 KV 不变所以可以缓存，但 cache 随长度线性增长、Decode 每步全量读取，瓶颈在显存带宽——GQA 把 KV 份数砍到四分之一，只省搬运不省 FLOPs；真正省 FLOPs 靠 Prefill 阶段的稀疏 Attention，前提是 kernel 执行前就跳块。第二是长度外推：能表示远距离不等于会用，Qwen2.5-1M 先练到 256K、再用 DCA 分块重组位置外推到 1M，和稀疏化分别解决「会读」和「读得起」。第三是训练稳定性：规模变大后打分膨胀使 softmax 单点独热，Qwen3 用 QK-Norm、Qwen3-Next 进一步上零中心 RMSNorm 和输出门控。第四是根本开销：N² 计算和线性增长的 cache 换成固定状态的线性注意力，牺牲无损召回换效率，Qwen3-Next 按 3:1 混搭分工，Qwen3.5 延续。

落到 Agent 开发：这些原理解释了我们每天的问题——为什么多轮之后 TTFT 变慢（prefill 增长、靠前缀缓存救）、为什么 1M 上下文不能取代 RAG（外推≠好用，且中间信息会丢）、为什么 Agent 需要精确召回（混合架构保留全注意力层的理由）。所以做 Context Engineering 时，我按「稳定前缀 + 受控尾部 + 外置记忆」来组织上下文，让模型架构的强弱项各得其所。
